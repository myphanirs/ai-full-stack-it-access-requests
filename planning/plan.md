# Build plan

## Choices

- **Runtime:** Python 3.12, with a dependency lockfile for any third-party packages; this matches the installed runtime and the repository's Python starter tests.
- **Interface:** a CLI with intake, queue inspection, history, resume, retry, refresh and accuracy-check operations; it fits the permitted interfaces and makes operator actions reproducible.
- **Test command:** `env -u API_KEY python3 -m unittest discover -s tests`; all tests use saved replies or an injected transport, with outbound networking blocked, following the starter test convention.
- **Model call:** an injected HTTP JSON provider adapter, configured with provider/model/request settings and reading API_KEY only at the live-call boundary; every planned test substitutes a transport or the mock provider. The supported provider's actual protocol and completion/refusal signals must be confirmed before implementing the adapter, rather than inventing a facilitator configuration.

This document proposes build work, not completed behavior or observed results. Only this plan is written now; fixture paths, commands and test names below describe future artifacts. No test or build step requires a real API key or a provider call. Tests of credential loading inject a dummy credential accessor without setting API_KEY. Package installation is a documented setup activity, not part of the offline tests.

**Decisions requested.** The unanswered Q-01–Q-94 in [spec.md](spec.md#open-questions) remain open. The [plan-from-spec skill](../.agents/skills/plan-from-spec/SKILL.md) requires: “Where a spec line is unclear, say so in the plan and ask the person; do not guess a rule.” Please resolve the business/acceptance questions before the dependent tests are finalized. The following gates identify dependencies; choices above select implementation tools, not answers to unclear business rules.

SQLite is a candidate for operators sharing one host; G2 must establish the deployment scope before committing to it. Consistent inspection and exported deliverables must refer to one recorded generation. This is an architectural proposal, not a source-imposed database requirement.

## Steps, in build order

Write each step's named tests before implementing that step, and observe their intended failure at the relevant interface, assertion or missing artifact. A failure caused only by an unrelated setup problem does not count. Run the owned tests after implementing the step and then run the existing suite. Each test ID below has exactly one owning step; later steps may run earlier tests without taking ownership. Resolve the listed gates before writing dependent assertions.

1. **Build the mock provider first.** Meets R-19 and supports R-20, R-23. Write **T-01** first: a future mock-provider interface cannot yet load/script the saved reply, failure and controlled-delay cases. Done when fixtures under `tests/mock_responses/` can drive deterministic completion, refusal, cut-off, error and barrier-controlled responses without keys or network, and calls can be counted. Mock setup must not perform extraction or routing itself.
2. **Read exports and capture source identity.** Meets R-04, R-33–R-37, R-56. Write **T-02, T-03** first, beginning with T-02 failing because export ingestion does not yet exist. ## Test plan

All paths under `tests/mock_responses/` below are planned fixture files, not files created in this planning step. Each saved success reply will contain a full schema-conforming extraction and the chosen provider envelope, including supporting_quotes and issues. Full completion/refusal/cut-off envelopes depend on G7. Expected business facts below were read from the exports, not obtained by running extraction. Saved replies and independent expected facts must be maintained separately so a comparison cannot simply read its oracle from the mock reply.

For each profile, document_id is its input filename and source_sha256 is independently computed from the original bytes. Supporting quotes must be exact substrings of decoded message text. The quoted fragments beside the facts are the evidence anchors, not a requirement that every model return the same quote array order or issue wording. Missing facts are established by inspecting the whole message; absence cannot itself be quoted. P § Extracted facts supplies the rule: “Represent absent or unresolved scalar values as null and explain each missing or conflicting fact in issues.” Exact text comparisons for purpose, quotes and issues stay gated by G5/G8.
